# Changelog

All notable changes to gsd-ng will be documented in this file.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed

- Roadmap phase fields written as `**Goal**:` — the colon *outside* the bold markers — are now read. `templates/roadmap.md` and `gsd-roadmapper` both emit that form for `Goal`, `Depends on`, `Requirements` and `Plans`, but the parsers in `roadmap.cjs` matched only `**Goal:**`, so a roadmap produced by GSD's own generator returned `goal: null` and `depends_on: null` from `roadmap get-phase` and `roadmap analyze` while `success_criteria` — parsed by a colon-outside pattern — came back fine. Downstream this was silent: `discuss-phase`'s todo linking skips when the goal is empty, and every other reader got `null` with no warning. Both spellings are now accepted everywhere, through a single `boldLabel()` helper in `bin/lib/core.cjs` rather than a per-site literal, since the two forms had already been reconciled in `core.cjs` and `phase.cjs` while `roadmap.cjs` was left behind — the drift is what the shared helper prevents. The colon-outside form remains what every producer writes; colon-inside is accepted because documents in the wild carry it.

- `roadmap update-plan-progress` and `phase complete` no longer report success while leaving the `**Plans**` line untouched. Both built their rewrite pattern with the colon inside the bold, so against a template-conformant roadmap neither matched: the progress table and the phase checkbox were updated, the detail section was not, and the command returned `{"updated": true, "complete": true}` — leaving a roadmap that claimed `1/1 Complete` in its table next to a detail line still reading `TBD`.

- The same two commands no longer rewrite a *later* phase's `**Plans**` line. The pattern walked from the phase header to the first `**Plans**` label through an unbounded lazy match, with nothing stopping it at the section boundary, so a phase carrying no `Plans` line silently absorbed the next phase's — attributing one phase's counts to another, which then read as complete. The search now stops at the next phase header. As a side effect the pattern no longer scans the whole document to fail: on a 20 000-header input it settles in 4 ms where the unbounded form took 6.9 s.

- A phase lookup no longer anchors on a longer phase number that appears earlier in the document. The pattern stopped at the digits it was given without requiring them to end there, so a single-digit lookup also matched a two-digit heading, a decimal child, and a letter-suffixed variant — and when one of those was written above the intended section, the update landed on the wrong one. The field-rewrite pattern now requires the number to end where it ends. The twelve other sites that interpolate a phase number were checked and left alone: each already has a literal `:`, `[:\s]` or `[.:]` immediately after the number, and appending a boundary to one of them would have broken it.

- `shannonEntropy` counted characters by code point but divided by the code-unit length, so for any text containing an astral character — an emoji, most obviously — the probabilities summed to less than 1 and the result was not an entropy. A window made entirely of astral characters was capped at 4.0 bits against a 5.5 threshold, meaning it could not be flagged however random it was. Counting is now by code unit, matching how callers slice their windows, which keeps the denominator equal to the window length and the ceiling at a stable 8.0 bits. Normalizing by code point instead would have made the ceiling vary per window and would have flagged an ordinary block of distinct emoji at 7.0 bits, trading a real false-positive source for a narrow detection gain. No file or corpus entry changes flagged state as a result; entropy findings remain advisory.

### Changed

- The false-positive entropy budget is measured over every window alignment rather than the detector's step-aligned ones. The budget counted how many corpus files the detector flags, but the detector walks fixed 256-character windows anchored at offset 0 and advancing by 128, so the count was a function of byte offset rather than of content: inserting seven blank bytes at the top of an otherwise untouched file re-aligned every window below it and moved a borderline file across the threshold, failing the suite on an edit that changed nothing dense. `scripts/fp-report.cjs` now measures the peak at stride 1, which no byte shift can move, screening with a rolling sum and rescoring candidates from exact integer counts so the result is identical bit for bit under any shift. The detector itself is unchanged and still samples every 128 characters — only the budget measurement is alignment-invariant. On the same corpus this reports 3 files where the anchored measurement reported 1, all three verified present beforehand with the same values; it is not a general upper bound, since partial tail windows are excluded and that gap is recorded in the budget file. `security.cjs` exports its entropy constants and helpers for the measurement to share, so the two cannot drift apart.

### Added

- The profile tables in `references/claude-model-profiles.md` are now checked against `MODEL_PROFILES` and `EFFORT_PROFILES` by a lint in the test suite. The reference doc is what agents and users read, the constants in `bin/lib/model-profiles.cjs` are what the engine resolves, and they were two hand-maintained copies of one mapping with nothing to catch a divergence — a doc that promised `opus` while the engine spawned `sonnet` would have read as correct on both sides. The lint parses the first pipe table under each definitions heading and compares agent list, order, and all three profile columns cell by cell, reporting the doc line number and both values on a mismatch. Its parser hard-fails on a renamed or reordered header row rather than comparing columns that no longer line up, and synthetic-input self-tests cover that case plus a drifted row, so the lint cannot pass vacuously if the doc's shape changes.

### Changed

- The `quality` model profile now tops out at `xhigh` rather than `max`. The four critical decision-makers — `gsd-planner`, `gsd-roadmapper`, `gsd-debugger` and `gsd-verifier` — move from `effort: max` to `effort: xhigh`; every other agent keeps `high`, and the `balanced` and `budget` profiles are untouched. `max` remains a valid tier and is still reachable per agent through `effort_overrides`, so nothing is lost for a workspace that wants it on a specific agent — it is simply no longer what a profile hands out by default. Existing installs pick the new value up the next time the effort sync runs (an install, `/gsd:set-profile`, or any `gsd config set effort_overrides.*`), which rewrites the managed `effort:` frontmatter in `.claude/agents/*.md`; a Claude Code restart applies it. The reference table in `references/claude-model-profiles.md` was updated alongside `EFFORT_PROFILES`, and the new sync lint above now holds the two together.

## [1.0.0-dev.20] - 2026-07-25

### Removed

- The `divergence` command is gone, along with its `/gsd:divergence` slash command, its triage state machine, and the `DIVERGENCE.md` artifact it maintained. It tracked how far a fork had drifted from its upstream and let you mark individual commits picked, skipped, deferred, adapted or already-covered. Nothing else in GSD read that state — it was a bookkeeping surface maintained by hand, parallel to the planning artifacts rather than part of them, and the triage table went stale the moment anyone rebased. `planningPaths()` no longer exposes a `divergence` entry, and the CLI now rejects `divergence` as an unknown command. There is no deprecation shim: a workspace with a `.planning/DIVERGENCE.md` keeps the file as an inert leftover and may delete it.

### Fixed

- `target_branch` is resolved through a single reader. `loadConfig()` normalizes the config's `git` block onto the top level, so a loaded config carries `target_branch` and never `config.git.target_branch` — but callers had drifted into three different spellings of the read, one of which reached for the nested path, got `undefined` every time, and silently fell through to `'main'`. The failure was invisible at the call site because a plausible branch name still came out.

  `resolveTargetBranch()` in `bin/lib/core.cjs` is now the only supported reader: it accepts a loaded config or a raw parsed `.planning/config.json`, applies one precedence order (caller overrides, then the flat key, then `git.target_branch`, then the fallback), and treats `null` and `""` as unconfigured rather than as a branch name. `loadConfig()` resolves its own field through the same helper, so the normalizer and its consumers cannot disagree by construction. `cmdSquash`, `resolveGitContext` (both the standalone and the submodule path) and the two `init` commands all call it. A structural lint fails the build if any shipped source under `bin/` reads `target_branch` off a config object directly, so a fourth reader cannot drift back in; a self-test on the detector keeps that rule from passing vacuously. The lint is line-oriented and says so — it is a tripwire against obvious re-introduction, not a proof that no reader exists.

- The submodule path in `resolveGitContext` no longer inverts the precedence it documents. It passed the *merged* global-plus-per-submodule block as the override layer, which promoted the global `git` block above the base config's flat top-level key — so `{"target_branch": "flatval", "git": {"target_branch": "nestedval"}}` resolved to `flatval` through `loadConfig()` and `nestedval` through `resolveGitContext()`, from one file. Only the per-submodule block is an override layer now, making the order `git.submodules.<name>` > flat `target_branch` > `git.target_branch` > the submodule's git tracking info > `main`, identical in both paths and as documented.

  One upgrade-visible consequence: the submodule path previously ignored a legacy flat top-level `target_branch` entirely, so a workspace using that spelling fell through to the submodule's git tracking info. Both spellings now resolve identically, which means such a workspace may see its submodule's resolved branch change to the configured value. That is the intended unification, but it is a behaviour change rather than a pure fix.

### Changed

- The meaning of the global `git.target_branch` in a submodule workspace is now written down in `references/planning-config.md`, where the workspace repo and the code submodule usually integrate into different branches. It has a dual role: it is the workspace repo's own integration branch, *and* it is the default that each `git.submodules.<name>` entry inherits when it sets no `target_branch` of its own. It is not a description of the submodule — when a submodule is the active git context, `git-context` and `init` report that submodule's resolved branch. The reference now recommends setting both keys explicitly when the two repos differ, rather than relying on inheritance, and states the full resolution order.

## [1.0.0-dev.19] - 2026-07-21

### Added

- The CI security scan now gates a pull request through a `security-gate` commit status instead of by flipping the `security-scan` check run. The old design mutated the check run Actions creates for the job, but GitHub only lets the app that *created* a check run update it, so whether the override's write would be permitted was a property of GitHub's authorization model rather than of this repository, and could not be verified offline. The verdict is now published as a commit status under the `security-gate` context on every run (`if: always()`), so a clean pull request produces a passing gate instead of hanging pending, and the override posts a *newer* `success` status under the same context — the latest status for a context wins, so an override supersedes rather than mutates, and any token with write access may post one, so nothing rests on undocumented behaviour. The workflow also lost its `paths:` filter, which could not coexist with the `security-gate` being *made* a required status check — a step that was described here as done but was never actually configured on the branch: a pull request touching no listed path never starts the workflow, so the required status is never posted and the pull request sits at "Expected — waiting for status to be reported" forever. That trap would have sprung on the first Dependabot bump, whose files (`package.json`, `package-lock.json`) the filter excluded; running the scan on every pull request — it is an API read and a regex pass with no build — removes the failure mode rather than compensating for it, while the scan-path list still decides which changed files are actually inspected. A verdict is now posted even when the checkout itself fails: the publish step loads the gate module from the workspace, which a failed checkout leaves empty, so a second step posts the status directly, reading nothing from the checkout, whenever the first did not succeed — without it a required gate would hang pending with no verdict, and the override could not rescue it either, since the override only supersedes an existing failing gate.

- The maintainer override (`/security-override:`) now requires the reviewed commit SHA and is safe as a standalone module. The command used to be recognised at the start of *any* line of a comment via an unanchored `/m` regex, and its only guard against a quoted or mid-body occurrence lived in the workflow file rather than the module — one edit away from being loosened, and absent for any second caller; matching is now anchored to the start of the untrimmed body, which also agrees with the workflow's own `startsWith` gate. More consequentially, the override read `pr.head.sha` at execution time, so a maintainer's approval of commit A could clear a failing verdict on a commit B pushed afterwards. Naming the reviewed commit is now mandatory — the SHA is the only statement that ties an approval to specific code — and an override with no SHA is refused with a message quoting the current head, ready to copy. The gate verdict's `created_at` is additionally compared against the comment's, and the override refused when the verdict is the newer of the two, since a maintainer cannot have been approving a verdict that did not yet exist; only platform-set timestamps are consulted, never the forgeable commit author and committer dates. The scanner's own failure output was corrected to advertise the pinned form, having still printed the unpinned one the SHA requirement now rejects.

- `import-issue` now honours the `--force-unsafe` flag it had long advertised. The error message in `commands.cjs` and three instructions in `workflows/import-issue.md` pointed maintainers at a flag that was never parsed — invoking it produced `Unknown flag`, so the documented escape hatch dead-ended. It now exists: with the flag, a high-confidence injection finding is warned about loudly on stderr and the import proceeds down the normal wrap-and-write path instead of aborting; without it, behaviour is unchanged. The flag bypasses the *gate*, not the detection or the audit trail — the scan still runs and its result is still written to `security-events.log`, unmodified except for a `forced: true` marker so a forced import stays distinguishable after the fact.

- `gsd-tools todo repair` moves a `completed:` line an earlier `todo complete` wrote *above* the opening `---` fence back inside the frontmatter block. That earlier writer prepended `completed: <date>` ahead of the opening delimiter, which defeats `extractFrontmatter`'s `^---` anchor, so every todo completed that way parsed as having no frontmatter at all — its title, area and completion date all unreadable. The writer is fixed at the same time (the date is now inserted *after* the opening fence, and a todo that arrives without a fence gets one), so `repair` exists only to reconcile the files the old writer already produced. It rewrites only the exact known-malformed shape — a leading `completed:` line immediately after the opening fence, an intact closing fence, and no existing `completed:` key inside — and skips and reports anything else. It is dry-run by default and applies only under `--write`, on the reasoning that a bulk rewrite of user data with no undo beyond git should be an explicit opt-in.

### Changed

- Permission rules are now normalized before being seeded into a user's `settings.json`, and the installer no longer emits a form Claude Code cannot match. Claude Code's file permission checks consult only `Edit(<path>)` and `Read(<path>)` rules; a `Write(<path>)`, `NotebookEdit(<path>)` or `Glob(<path>)` rule parses fine but is never matched, and since CC 2.1.210 each one also draws a startup warning — for `allow`, `deny` and `ask` alike. Such a rule is dead weight twice over: it reads as policy, never fires, and costs the user a warning on every launch. A new `normalizePermissionRules` helper in `bin/lib/allowlist.cjs` rewrites each unmatched form to its effective spelling (`Edit(<path>)` for the file-editing tools, `Read(<path>)` for `Glob`) and de-dups the result, and `install.js` now runs *all three* sections through it rather than only `deny`. The de-dup is what neutralizes the `Edit(.env)` + `Write(.env)` *pair* shape an earlier plan proposed — the redundant half collapses into the real rule instead of surviving as decoration. A **bare** tool-name rule such as `Write` is deliberately left alone: with no path it matches the tool everywhere and draws no warning, so it is a working construct, and rewriting one would silently change a correct rule's meaning. `Read(<path>)` is likewise untouched, being a separate and genuinely enforced rule that should stay alongside `Edit(<path>)` for secrets.
- The concrete bug this fixes: macOS and Windows installs were seeding `Write(*)` into `permissions.allow`, so every such install running CC 2.1.210 or later drew a startup warning for a rule that never did anything. `getReadEditWriteAllowRules` now returns `['Edit(*)', 'Read(*)']` off Linux, and `Write(*)` is gone from `templates/settings-sandbox.json`. The grant is moved, not withdrawn — one `Edit(*)` rule already governs every built-in file-editing tool, the Write tool included. Linux is untouched and still receives bare `Edit`, `Write`, `Read`: bare forms are the existing workaround for the Linux glob handling in claude-code#16170 and #6881, and because a bare rule is effective and warning-free there was no reason to disturb the one platform with a documented history of permission-engine quirks. A companion `findUnmatchedPathRules` backs assertions that fail the build if an unmatched form is ever authored into the template, or reaches a seeded `settings.json` on any platform — catching the mistake at source and at the point it would ship, rather than relying on the installer to repair it.
- The `generate-allowlist` command now normalizes its output the same way the installer does. Both writers read the same `templates/settings-sandbox.json` and both append the platform-appropriate Read/Edit/Write forms, but only `install.js` ran the result through `normalizePermissionRules` — `generate-allowlist` filtered the canonical forms and emitted everything else verbatim. Nothing leaks today, since the unmatched `Write(*)` form is gone from both the template and `getReadEditWriteAllowRules`, so the two outputs happen to agree. That agreement was accidental rather than structural: an unmatched path form authored into the template in future would have been sanitized on the install path and passed straight through on the generate path, and the existing set-equality parity tests would not have noticed, because they compare the two writers against each other on a template that contains no such form. Both writers now sanitize, and the parity tests additionally assert that *neither* output contains an unmatched path form — an assertion about the rules themselves rather than about the two writers agreeing, so it still holds if the template changes.
- Known limitation: this governs only what GSD *seeds*. The allow/deny/ask sync is union-only, so a pre-existing unmatched rule in a user's own `settings.json` — a hand-written `Write(.env)` deny, say — is left exactly as it is: neither rewritten nor reported. Such a rule will keep drawing its startup warning, and a `Write(<path>)` deny in particular will keep reading as protection it does not provide. Repairing rules GSD did not write is deferred to the manifest migration mechanism, alongside the other in-place settings rewrites.

### Fixed

- A phase's plan counter no longer stalls when more than one plan finishes at a time. `state advance-plan` read `Current Plan`, added one, and wrote the result back — correct only if plans complete strictly one after another, which is not how `/gsd:execute-phase` runs them. Waves are parallel by design, so N executors finishing together each read the *same* stored value before any of them writes, and all N write that value plus one. A five-plan wave advanced the counter by one. The symptom is that STATE.md points at a plan that was finished long ago, and everything reading it inherits the error: `/gsd:progress` and `/gsd:resume-work` route to already-completed work, and the position shown on resume is quietly wrong rather than obviously broken — nothing errors, so the drift is only noticed when someone re-executes a plan that already has a SUMMARY. It went unseen because a phase whose waves each hold exactly one plan behaves correctly, and the workaround was a per-phase instruction telling executors to call `update-progress` instead — a footgun avoidable only by remembering to avoid it.

  The position is now derived rather than incremented. `advance-plan` counts `*-SUMMARY.md` files in the current phase directory the way `update-progress` already counts them, and sets `Current Plan` to that count plus one — the caller writes its own SUMMARY before invoking this, so the count includes the plan just completed. Every concurrent caller reads the same disk state and computes the same answer, which makes the outcome independent of who wins the write race; it also makes a repeat call a no-op, so an executor retried after a failure can no longer skip a plan. Last-plan detection moved to the same footing: the phase is complete once the SUMMARY count reaches `Total Plans in Phase`, so a wave that finishes the phase reports `Phase complete — ready for verification` from every executor in it rather than from whichever one happened to hold the final increment. The phase is located from `Current Phase`, falling back to the prefix of a compound `Current Plan` such as `64-02`.

  Both STATE.md dialects and every stored plan format are preserved, since the derived number is rendered into the shape already on disk: `02-08` becomes `02-09`, `08` becomes `09`, bare `8` becomes `9`, and the compound `Plan: 2 of 6 in current phase` line keeps its wording. Where the phase directory cannot be found — no `.planning/phases` entry for the current phase, or a project not laid out that way — the command falls back to the previous in-place increment rather than failing, and `--json` now reports `derived_from_disk` and `completed_plans` so a caller can tell which path ran.

  A backwards correction is no longer reported as an advance. Deriving the position from disk can legitimately land *behind* the stored value — a STATE.md claiming more progress than the summaries on disk support gets corrected downwards, which is how a retried or partially-failed run recovers. But the correction was reported as `advanced: true` with a `current_plan` lower than `previous_plan`, and in plain-text mode it printed `true`, byte-identical to a real advance. A STATE.md at plan 4 of 5 with no summaries on disk rewound to plan 1 while every layer reported success, which is enough to silently restart a phase from the beginning.

  `advanced` now means forward movement and nothing else. A rewind reports `advanced: false` with `rewound: true` and `reason: "rewound"` — the reason field because `advanced: false` already signals the last-plan case, and the two must stay distinguishable — and prints `rewound` rather than `true`. An idempotent re-run — one that recomputes the position already on disk and moves nothing — is likewise no longer reported as an advance: it comes back as neither advanced nor rewound, with `reason: "idempotent"` and a plain-text `unchanged`, so the three non-advancing outcomes (last plan, rewind, no-op) stay distinguishable from one another and from real forward movement. A caller that branches on `advanced` alone now declines to treat a correction as progress instead of being misled by it. The derived position itself is unchanged and still correct; only the report changed. `/gsd:execute-plan` and the executor agent describe what a rewind means and tell the executor to establish why STATE.md and the phase directory disagreed rather than continuing from the rewound position — their previous unqualified claim of idempotency was what made a silent rewind dangerous.

  One related hazard is *not* addressed here and is worth naming: `advance-plan` still rewrites STATE.md as a whole-file read-modify-write, so a concurrent `add-decision` or `add-blocker` landing inside that window can still be lost. That is a narrower race than the counter — it needs two writes to interleave, rather than being guaranteed on every parallel wave — and closing it properly means serializing all STATE.md writers behind a lock, not patching one command.

- A requirement no longer reads Complete while most of its work is unstarted. Requirements were closed as a per-plan side effect: the last step of every `execute-plan` run took the finishing plan's own `requirements:` frontmatter and ran `requirements mark-complete` on it. That is fine only if each ID belongs to exactly one plan, which is not how phases are planned — several plans routinely share one requirement, each contributing a slice of it. Whichever of them finished *first* closed the ID for all of them. Under the wave-based parallel execution `/gsd:execute-phase` performs by design, "first" is not even a meaningful ordering; it is whichever subagent happened to win the race. The reported case was a 13-plan phase where all 13 declared the same consolidation requirement and the real work lived in plans 06 through 13 — the requirement was marked `[x]` and its traceability row flipped to Complete when plan 02 finished, a characterization-test plan that modified zero production files. The damage is that it is *silent and downstream*: the phase verifier and the REQUIREMENTS.md traceability table both then report a satisfied requirement, and a row marked Complete on first-plan-wins is indistinguishable from one that was genuinely verified, so the table stops being evidence of anything. It was caught at all only because that phase's executors had been explicitly told to check the flag and revert it by hand.

  Closure is now a phase-close action carried out once by `gsd-tools phase complete`, on the verifier's authority — which is how completion is judged everywhere else in GSD, `getPhaseCompletionStatus` included. The per-plan step is gone from both `execute-plan` and the `gsd-executor` agent; a plan's `requirements:` frontmatter goes back to being the declaration of intent it reads as. Two changes keep the later closure from becoming a *never*-closes bug in exchange. First, `phase complete` no longer takes its IDs solely from the ROADMAP phase section's `**Requirements:**` line, which is frequently absent — it closes the union of that line and the `requirements:` frontmatter of every PLAN.md in the phase, deduped, so the plan-declared IDs that the per-plan hook used to handle are still picked up. Second, an absent VERIFICATION.md does not block closure: verification is a qualifier, not a gate, so a project running with `workflow.verifier` off behaves exactly as before. What *does* withhold closure is a VERIFICATION.md that reports `gaps_found` or `halted` — the verifier has looked and says the goal is not met, so every ID stays Pending and the table keeps telling the truth until the gaps are closed and the verifier re-runs, at which point a repeat `phase complete` picks them up. `human_needed` is deliberately not treated as failing, since it means the automated checks all passed and `execute-phase` only reaches phase-close after the human approves. The operation is idempotent — IDs already Complete match neither the checkbox nor the traceability pattern — so re-running a phase is a no-op, and `phase complete --json` now reports `requirements_closed`, `verification_status`, and `requirements_blocked_by` so the caller can see which of these applied.

  A side effect worth naming: closing requirements once per phase also removes an unsynchronized read-modify-write on REQUIREMENTS.md. Concurrent executors in the same wave each rewrote the whole file, so one agent's edit could silently drop another's.

- A phase no longer closes requirements that belong to a phase which has never run. Closure matched traceability rows on the requirement id alone — the phase column was skipped over by the pattern and never compared against the phase being closed. Combined with the union that gathers ids from plan frontmatter as well as the roadmap, any plan that declared an id the traceability table assigns *elsewhere* closed it: the checkbox was ticked and the row flipped to Complete for work that was not merely unfinished but unstarted, in a phase nobody had executed. This is the same class of defect as the per-plan closure fixed above, and the fix for that one made it more visible rather than less — closure was consolidated into a single phase-close action so the table would stop lying, and it stopped lying *within* a phase while still lying *across* phases. A plan overreaching in its `requirements:` frontmatter, which is a declaration of intent and not a verified claim, was enough to trigger it.

  The traceability table is now the authority on which phase owns an id, and the candidate list from the roadmap and plan frontmatter only proposes. Each candidate falls into one of three cases. If the table gives it a row for the phase being closed, it closes as before. If the table gives it a row for a *different* phase, nothing is written — and, importantly, it is **reported** rather than silently dropped, in a new `requirements_other_phase` field of `phase complete --json`, because a quiet skip is a quieter version of the same problem: the plan believes it delivered the requirement, the owning phase may never run, and nobody is told. If the table has no row for it at all, nothing can contradict the plan, so the checkbox still closes and the id comes back in a new `requirements_unmapped` field flagging the coverage gap. The third case is what keeps a project whose REQUIREMENTS.md has no traceability table working exactly as before, and keeps the roadmap-declared ids closing for a phase whose roadmap section omits its requirements line — the case the union exists for. `/gsd:execute-phase` surfaces both new lists to the user.

  The phase column is compared semantically, not textually, since the column is free text and is written inconsistently across projects — zero-padded, unpadded, decimal, letter-suffixed, and any of those optionally prefixed with the word "phase" all appear, and decimals introduced by an insert make plain string equality useless. Values are normalized through the same comparison the rest of GSD sorts phases with. Where the cell labels its numbers with the word "phase", only the labelled ones count, so a number in a parenthetical cannot be mistaken for a phase reference. Two smaller cases follow from reading the table properly rather than pattern-matching it: a row whose status is `Blocked` is left alone, since that is a human decision closure has no business reverting — and *left alone* now reaches the checkbox and the reported result, not just the row text. An earlier version preserved the `Blocked` row but still ticked the requirement's `- [x]` box and reported the id closed, so the document contradicted itself with a checked box above a `Blocked` row that disagreed with it; the id now drops out of closure entirely — no row write, no checkbox, absent from the closed set — and is surfaced in a `requirements_blocked_rows` list rather than silently ticked, with the `updated` flag derived by diffing the rendered document against what was read so it no longer claims a write a wholly-`Blocked` candidate set never made. An id split across several phases has its own row closed but its checkbox left unticked until no row still attributes outstanding work elsewhere.

- A requirement no longer closes because a plan *said* it would deliver it. Closure gathered its ids from each PLAN.md's `requirements:` frontmatter, which is a statement of intent written before execution — a plan that declared an id and then deviated during execution still contributed it, and a plan that never ran at all contributed its ids just the same, provided some sibling plan in the phase had a SUMMARY. That the two were usually in agreement was an artifact of `execute-plan` instructing the executor to copy the plan's array into the summary verbatim; "usually identical because a workflow says to copy it" is a convention, not a derivation, and the entire point of moving closure to phase-close was to stop closing on intent. Closure now resolves each plan against the SUMMARY that records its execution. A plan with no paired summary has not completed and contributes nothing — the same completion test `getPhaseCompletionStatus` applies everywhere else. A summary that carries `requirements-completed:` supplies the ids, because that field is the record of what actually landed. The three ways a summary can fail to name ids are now told apart, because collapsing them was itself a hole. An **absent** field falls back to the plan's declaration: the field is recent and postdates a large body of existing summaries, so a record written before it existed makes no claim either way, and failing closed on that silence would have stranded the requirements of every phase written before it, converting a latent inaccuracy into an active outage. An **explicitly empty** field is a written claim to have delivered nothing, so it closes nothing and is reported in `requirements_empty_summaries` rather than being read as permission to close everything. An **unreadable** summary — a read failure, or a frontmatter block opened and never closed — closes nothing and is reported in `requirements_unreadable_summaries`: a truncated or corrupt record is not evidence of delivery, and the earlier fall-back-to-declaration behaviour let a corrupt SUMMARY close the plan's full declaration, the exact failure the delivery-record mechanism exists to prevent. A document with no opening delimiter at all is merely frontmatter-less rather than corrupt, and stays in the absent case. An id a summary claims that its plan never declared still closes — the summary is the delivery record and outranks the declaration — but comes back in a new `requirements_undeclared` field, following the precedent set by `requirements_other_phase` and `requirements_unmapped` that a discrepancy is surfaced rather than silently accepted; it means scope grew during execution, and the roadmap or the requirement's owning phase may now be wrong. The ROADMAP phase section's `**Requirements:**` line remains a third source and is still unioned in, since a phase whose plans carry no `requirements:` would otherwise never close anything, but it is now admitted only once *every* plan in the phase has a summary — it is a phase-level declaration rather than a delivery record, so while any plan is still outstanding it describes work that has not all landed.

- A stale failing verification no longer blocks requirement closure without saying so. Closure is withheld when VERIFICATION.md reports `gaps_found` or `halted`, which is correct — but if the gap-closure plans are then executed with `workflow.verifier` disabled, nothing rewrites the report, and the original failing verdict blocks closure indefinitely. The user sees `requirements_blocked_by: gaps_found` and has no way to tell it from a current verdict, so the natural reading is that the gaps are still open and the remedy is to fix them again; the only actual escape was the retained manual `requirements mark-complete`. `phase complete` now compares the report's mtime against every SUMMARY.md in the phase and reports `verification_stale` plus `verification_stale_summaries` naming the files that postdate it, and `requirements_blocked_hint` carries a message stating that the report cannot reflect that work and that the remedy is to re-run verification. Closure is still withheld. Auto-closing on a stale-looking report was considered and rejected: a report's age is not evidence that its gaps were closed, mtimes are weak evidence in the first place (a fresh clone or checkout rewrites all of them), and any rule of the form "a failing verdict expires once newer work appears" makes the gate bypassable by executing anything at all afterwards — which is the same as having no gate. The defect being fixed is that the block was undiagnosable, not that it existed, so the fix makes it legible and points at the remedy without weakening it. Staleness is reported wherever it is observed, including on a passing report, since a pass that predates later work is equally uninformative about the phase as it now stands.

- The installer no longer reports GSD's own agent-file rewrites as local user modifications. `.claude/gsd-file-manifest.json` recorded a plain sha256 for each deployed `agents/*.md`, but those files are rewritten by GSD itself whenever a supported config change lands: `/gsd:set-profile` and `gsd config set effort_overrides.*` both call the effort sync, which re-serialises the *entire* frontmatter block — the managed `effort:` value changes, YAML comments drop out, and values pick up canonical quoting. Any such change therefore guaranteed a hash divergence, and the next install stashed all 15 agent files into `.claude/gsd-local-patches/` and advised running `/gsd:reapply-patches` for edits the user never made. The noise was not merely cosmetic: an update that stashed 16 files, 15 of them false positives, left the one genuine local patch indistinguishable from the rest — and a warning that cries wolf 15 times out of 16 trains you to skip the time it matters. Agent entries now carry a second, normalised hash taken over the canonicalised frontmatter with the GSD-managed keys removed, plus the untouched body, and the installer consults it before calling a raw mismatch a user edit. A profile or effort-override switch is thus invisible to patch detection, while a real edit to an agent's prompt body is still detected and backed up — including when it sits in the *same* file as a config-driven frontmatter rewrite, since the body is what the normalised hash covers. The new `files_normalized` map is additive and optional, so no manifest schema bump was needed: a manifest written by an older installer carries no such map and simply keeps the previous raw-hash verdict.

  One edit is now missed, and it is worth stating plainly: because the canonicalising pass drops YAML comments, a change made *inside* a commented-out frontmatter line is normalised away and is neither reported nor backed up. Agent files ship a commented `# hooks:` block that invites that customisation, so this is reachable rather than theoretical — although uncommenting the block, which is the more likely edit, alters real keys and is still detected. A hand-set `effort:` is likewise no longer flagged, which is intended: GSD overwrites that value on the next config change or install regardless.

- The "▶ Next Up" continuation blocks no longer print raw `<sub>` tags into the terminal. The subtext line under every continuation prompt — usually `` `/clear` first → fresh context window `` — was wrapped in `<sub>…</sub>` to de-emphasize it, which works on GitHub but not where these blocks actually land: Claude Code renders GitHub-flavored markdown in a terminal, and GFM does not support inline HTML. The tag was never interpreted, so users saw the literal characters `<sub>` and `</sub>` bracketing the hint on essentially every command that ends by suggesting a next step. All 43 occurrences across 22 files are now `*italics*`, which matches the repo's existing italic convention and renders correctly in both the terminal *and* on GitHub; the swap is a pure delimiter change, preserving the inline-code backticks, the `→` arrow, and the two-space indentation at the three nested sites. One site in `agents/gsd-planner.md` that had drifted to a hyphen separator was normalized to the arrow at the same time. Guarding the fix, a new `tests/terminal-html-lint.test.cjs` bans the nine rendering-only inline tags (`sub`, `sup`, `small`, `kbd`, `mark`, `br`, `u`, `font`, `center`) across workflows, agents, and the two terminal-facing references, and `gsd-ng/references/continuation-format.md` gained a format rule stating that subtext uses italics — without it the pattern reintroduces itself the next time someone copies the continuation format. The lint deliberately does **not** ban `<details>`/`<summary>`: workflow files legitimately emit those as content written *into* ROADMAP.md, which is read on GitHub where HTML does render, and `<summary>` additionally collides with a GSD XML structural tag — so a blanket "no HTML in workflows" rule would have broken real usage. It likewise skips inline code spans and fenced blocks declaring a source-code language, so prose documenting the banned tags and JSX examples are not flagged.

- `todo add` no longer silently discards a repeated flag. Every flag in the dispatcher was read with `args.indexOf(flag)`, which finds the first occurrence and nothing else, so `todo add --title T --files "x.js" --files "y.js"` wrote a todo whose `files:` list contained only `x.js` — while the comma-separated `--files "x.js,y.js"` correctly wrote both. Repeating a list flag is a standard CLI idiom rather than a misuse, which makes this easy to reach, and the failure is the worst kind: no warning, no error, and a todo that reads as complete while quietly missing half its metadata. It is caught only by re-reading the file afterwards. That is also precisely the failure mode `todo add` was written to eliminate — the verb errors on a filename collision *naming the existing file* rather than overwriting it, on the reasoning that the hand-rolled `Write` path it replaced clobbered data without saying so; dropping a repeated flag lost data the same way, one field lower down.

  Repeated flags are now handled according to what the flag means. `--files` and `--related` are lists, so repeats **accumulate**: a new `listFlag` helper joins every occurrence into one comma-separated string before it reaches the existing `splitList`, making `--files a --files b`, `--files a,b`, and the mixed `--files a,b --files c` all produce identical frontmatter. Accumulating was preferred over erroring because it is what a user typing the flag twice already means, and it costs nothing — both idioms now work rather than one of them being legislated away. The single-value flags (`--title`, `--area`, `--phase`, `--body`, `--body-file`, `--interval`) take the other branch, since appending a second title is meaningless: a repeat is now an **error naming both conflicting values**, which is the same stance as the collision check. The boolean `--recurring` is untouched, being idempotent under repetition.

  This is deliberately scoped to `todo add` rather than applied dispatcher-wide. The `args.indexOf` idiom backs roughly seventy flags across every verb, and rewriting all of them in one pass would change argument handling for commands whose first-wins behavior may be load-bearing, with no test to say which. The two helpers (`listFlag`, `scalarFlag`, over a shared `collectFlagValues`) are written generically and documented for other verbs to adopt as they are touched, so the fix is reusable without the blast radius.

- `todo complete` now accepts a todo id with or without its `.md` extension. It joined the argument straight onto the pending directory and checked for existence, so `todo complete 2026-07-18-some-slug` failed with `Todo not found: 2026-07-18-some-slug` for a todo that was sitting right there — the message named the id it was given and stopped, offering nothing to suggest that a three-character suffix was the entire problem. Since the bare slug is what appears in prose, in filenames-minus-extension, and in anything a user types from memory, the error was routinely read as "the todo is gone" rather than "add `.md`". Resolution now tries the id as given and then with `.md` appended, and when neither exists the error names every candidate it looked for and the directory it searched, so a genuine miss is distinguishable from a formatting one. The resolved on-disk basename — not the abbreviated id the caller typed — is what flows downstream, so the file written into `completed/`, the `--json` `file` field, and the recurring path's `recurring-reset:` line all report the real filename. The sibling subcommands do not share the asymmetry and needed no change: `todo list-by-phase` and `todo scan-phase-linked` take a phase number, and `todo complete` is the only verb that accepts a todo filename from the user.

- Uninstalling GSD no longer leaves its own files behind in `hooks/`. `--uninstall` removed Claude hooks by matching against six filenames written out by hand in `install.js`, and `hooks/bash-safety-hook.cjs` was not among them — so the PreToolUse bash-safety hook GSD installs on every Claude install survived both `--uninstall` and the `--clean` wipe. A user who removed GSD was left with an orphaned executable hook that nothing would ever update, clean up, or account for, still wired into `settings.json` and still running on every Bash tool call. The omission was almost certainly because the file is the one GSD hook without a `gsd-` prefix. The same audit turned up a second survivor on *both* runtimes: `gsd-file-manifest.json` was deleted by the `--clean` wipe but never by `uninstall`, so every uninstall left GSD's own bookkeeping file in the config directory. Both are now removed, and `uninstall` additionally strips the `bash-safety-hook.cjs` entry from `settings.json` — without that, fixing the deletion would have traded an orphaned hook for a dangling `PreToolUse` command pointing at a script that no longer exists.

  The hardcoded list had the inverse defect too, and it is the one worth fixing structurally: a hook renamed or retired in an earlier release matches neither the deletion list nor any currently shipped filename, so it is stranded by the wipe *and* by the install and persists forever. The list was evidence of this in itself — `gsd-check-update.sh` sat in it only to clean up an artifact of a release predating the `.js` rename, a reactive patch applied after the fact. The removal set is now derived from what GSD actually installed rather than from names typed into the source: the manifest gained an additive `installed_hooks` record of the hook files each install wrote, and the wipe removes exactly those. A retirement is therefore self-cleaning from here on — the release that stops shipping a hook still removes it, because the install that put it there recorded it — with no list to remember to update. Two fallbacks back that up: the filenames the running package ships, for installs whose manifest is absent, unreadable, or predates the record, and a small `RETIRED_GSD_HOOKS` list repurposed from the old hardcoded one, which now carries only the names retired before the manifest began recording hooks.

  `installed_hooks` is deliberately kept out of the manifest's `files` map rather than folded into it. `files` drives local-patch detection, so listing hooks there would have quietly enrolled them in modification backup — a real behavior change to what lands in `gsd-local-patches/`, arriving as a side effect of a deletion fix. Being additive, the new key needs no schema bump and is ignored by older installers. Removal remains exact-filename throughout, never a prefix or glob: the obvious-looking alternative of matching `hooks/gsd-*` the way `agents/gsd-*.md` is matched would not have covered `bash-safety-hook.cjs` at all, and would have started deleting a user's own hook if they happened to name it with a `gsd-` prefix. Renaming the file to `gsd-bash-safety-hook.cjs` was rejected on the same grounds it was tempting — it makes the glob work, but it *is* the retired-filename problem, requiring the old name to be carried for at least one release, which is exactly what the manifest record now handles generically. New tests assert the invariant nothing previously checked: after `uninstall`, no file GSD installed remains on either runtime, with `settings.json` — the runtime's own config file, which GSD merges into and strips rather than owns — the sole documented survivor.

- A pull request that plants prompt-injection content in an agent file is now caught, where previously it was neither scanned nor even able to start the scan. The CI security scan matched changed files against `.planning/`, `.claude/`, `.github/` and `scripts/` — a path list carried over from the *installed* layout, where `.claude/gsd-ng/` is where GSD's agent-facing files live, and never adapted to the source layout of this repository, where the first two directories do not exist at all. Real coverage was therefore `.github/` and `scripts/` alone: 21 of 333 tracked files, about six percent. Every directory that actually becomes agent context was outside it — `gsd-ng/` (128 files), `commands/` (42), `agents/` (15), `hooks/` (6). A pull request rewriting `agents/gsd-executor.md` to carry injected instructions was not scanned. Worse, the workflow's `paths:` trigger used the same list, so such a pull request did not start the workflow in the first place and the check reported nothing rather than reporting a pass — there was no failing signal anywhere to notice. Scanning now covers every tracked directory whose contents are read as instructions, plus `AGENTS.md` and `CLAUDE.md` at the root, taking coverage to 219 of 333 files. `.planning/` and `.claude/` are retained even though untracked here, so a change that introduces them is covered from its first commit.

  Two directories are deliberately left out and the reason is not incidental: `tests/` and `benchmarks/` hold the detector's own fixture corpus, files that exist precisely to contain attack strings, and scanning them would report the fixtures as attacks. Widening to everything else costs almost nothing — over the 212 files added to scope the whole tracked tree yields two high-confidence files and twelve medium findings, so neither false-positive volume nor CI runtime was an obstacle. Those two files are `gsd-ng/bin/lib/security.cjs` and `gsd-ng/references/security-untrusted-content.md`, which trip the rules because they *are* the rules and their written reference; without relief the repository would block its own security work. Exemption is no longer by whole path, though, and the reason is not incidental: `security-untrusted-content.md` is `@`-included into `import-issue`, `sync-issues` and `create-pr`, so its full text loads straight into an agent's context — the most attractive file in the tree to poison was the one a path exemption spared, along with every future line an attacker might append below the reference's real content. Being listed now exempts *nothing* on its own; it only means fenced marker lines are honoured within that file, and only the text between a matched start/end pair is spared. The decision is per pattern — a rule that still fires once the marked regions are removed is firing on unexempt text, even when the same rule also matches a quoted example inside a region — and an unterminated region exempts nothing rather than running to end of file, so a lone start marker cannot shelter the rest of a file. Both files are still fully scanned, with every finding emitted as an annotation; the exemption removes the failure, not the signal. Root markdown files were later brought into scope on the same criterion that already covered `docs/`: `README`, `CONTRIBUTING`, `SECURITY`, `CHANGELOG` and `VERSIONING` had gone unscanned because the path list named directories plus the untracked `AGENTS.md` and `CLAUDE.md` and structurally could not see a tracked root file, so they are enumerated from git and scanned too.

  The test that was supposed to guard this asserted only that the script's path list and the workflow's trigger agreed with each other, which they did — it was enforcing consistency between two equally wrong lists, and passed throughout. It now asserts the property that matters: every tracked top-level directory must be scanned unless it appears in an explicit, justified non-context list, so a new directory added to the repository fails the suite until someone either covers it or states why it is not agent context. Set-equality with the workflow trigger is kept as a separate assertion, because that is what stops the two drifting apart again — a path scanned by the script but missing from the trigger never causes the workflow to run at all.

- The CI security scan no longer stops reading a pull request after its first hundred changed files, and no longer skips a file whose diff the GitHub API declines to return. The changed-file list was fetched with `per_page=100` and the response's pagination links were never followed, so on a pull request of 150 files the last 50 were silently unscanned — no warning, and a summary line reporting a clean scan of the files it *did* read. Pagination is now followed to the last page, and completeness is proven by comparing the retrieved file count against the pull request's own `changed_files` — a short list is refused as an incomplete scan, which blocks but is reported distinctly from a detection, on the reasoning that a scan reporting success over an unstated subset is worse than one that refuses. The former thirty-page cap survives only as a runaway-pagination guard: thirty pages of a hundred is exactly GitHub's own three-thousand-file ceiling on that endpoint, so the cap alone could never trip before the API stopped paginating, which is why the count check rather than the cap is what now guarantees the diff is whole. The scanner also used to feed the raw unified-diff text to the detector, but the `+` prefixing each added line interrupts the whitespace runs the patterns join words across, so a payload split over two added lines matched as ordinary file content yet slipped through as patch text. It now reconstructs the post-change file text first — dropping hunk headers and removed lines and stripping the leading `+` or space — which both closes that gap and stops a patch that *deletes* an injection from being reported as introducing one. Separately, the scanner read each file's `patch` field and `continue`d when it was absent — and the API omits `patch` for oversized diffs and for anything it classifies as binary, which makes that branch a padding bypass: inflate a file past the diff limit and its contents are never examined. The scanner now falls back to fetching the file's full contents at the pull request head commit, which scans strictly more than the patch would have, and fails closed with a blocking annotation only when that also cannot be retrieved. Fetching the blob was preferred over failing closed outright because patch omission is routine and legitimate; blocking every large refactor and every asset added under a scanned path would have trained maintainers to reach for the override, which destroys the signal more thoroughly than the bypass did. An added file that is genuinely empty is distinguished from one that could not be read, so it is not reported as a failure. None of this changes the trust model: the workflow still runs on `pull_request_target`, still checks out the default branch with no `ref`, and still executes no pull request code — reading a blob widens what is *read*, not what is run.

  The reason all of the above went unnoticed is that the script had no tests and could not have had any: it read its environment variables and called `process.exit` at module scope, and exported nothing, so merely requiring it terminated the test process. It is now structured so the parts worth testing are pure and exported — path matching, exemption matching, `Link` header parsing, pagination, and the scan-and-annotate pass, which takes an injectable content fetcher — while the environment read and the process exit happen only under a `require.main` guard. The suite now drives the scanner directly, including the case the original defect allowed: injection content planted in a file under `agents/` and under `gsd-ng/` is asserted to be in scope, scanned, and blocking.

- Invisible characters no longer bypass injection detection. `normalizeForScan` applied NFKC and homoglyph folding but left zero-width and bidi control characters in the text, so a single invisible codepoint dropped inside a keyword broke every high-tier regex while an LLM read the string unchanged: a canonical override phrase scanned as tier `high` with two blocked rules, while the same phrase carrying one `U+200B` inside its first word scanned as tier `medium` with none. That downgrade slipped the Rule-of-Two gate in issue-import and would have let the CI scan report success on a poisoned pull request. Normalization now strips `\p{Cf}` — the zero-width set, bidi marks, embedding/override/isolate controls, soft hyphen, byte-order mark, and the TAG block used for ASCII smuggling — plus the variation selectors, before folding, while leaving general combining marks alone since they carry visible meaning. A follow-up closed a second class the `\p{Cf}` strip missed: thirteen codepoints that render with no advance width but sit in other Unicode categories — the combining grapheme joiner, the Hangul and Khmer fillers, the Braille blank pattern, and the free-standing Mongolian and other variation selectors — each of which took that same test phrase from tier `high` to tier `clean` with no finding at all, worse than the zero-width case which at least tripped the retained detector. They are now removed by explicit list. That zero-width and bidi detector still runs against the *original* content, so the mere presence of such characters is logged as its own signal even though they no longer perturb the keyword match.

- `wrapUntrustedContent` no longer lets a body break out of its own containment. The wrapper interpolated untrusted text between its `<untrusted-content>` tags with no escaping, and no detector pattern matches a bare `</untrusted-content>`, so a body carrying its own closing tag scanned clean and was emitted verbatim — the attacker's prose then sat *outside* the boundary in a file agents read as project state, with no banner and no logged event. Every `<` that would begin an untrusted-content tag is now escaped to `&lt;` before wrapping, which also neutralises a dangling `<untrusted-content` with no closing `>`, and the `source` attribute is escaped on the same footing.

- Untrusted values can no longer inject YAML frontmatter keys. Several writers interpolated attacker-controlled strings into frontmatter without the escaping `yamlScalar` provides, and `yamlScalar` itself only quoted control characters, `:` and `#`. Issue *titles* were the widest hole: only the issue body was wrapped, so a title went raw into the agent-facing JSON and — unquoted — into the todo's YAML frontmatter, and a tracker that permits newlines in titles (self-hosted Forgejo or Gitea) could thereby inject arbitrary frontmatter keys. The title now takes YAML quoting rather than a wrapper, since it is a single-line field, and `yamlScalar` now treats control characters as forcing quotes so an embedded newline cannot end the scalar; an `untrusted_title: true` marker sits beside it, documented in `references/security-untrusted-content.md` with a reader so an agent knows to treat the value as untrusted data and to preserve the marker when it rewrites the todo, and the issue `number` is coerced rather than trusted. `yamlScalar` was hardened against the values a line-based reader tolerates today but a real YAML parser would reinterpret — a leading indicator character (`-`, `?`, `&`, `*`, `[`), boolean- and null-like words (`yes`, `null`), numeric- and timestamp-looking values, and the Unicode line separators `U+0085`/`U+2028`/`U+2029` — so a title, name or area cannot smuggle a sequence, anchor, alias, boolean or a second field into the block. The remaining hand-quoted sites were routed through it: `cmdScaffold`'s `--name` and `--phase` (a non-numeric `--phase` passes through `normalizePhaseName` unchanged and reached the frontmatter writes unescaped), and issue-import's `area` — taken from the issue's first label, lowercased but otherwise attacker-controlled — and `external_ref`, which had been hand-wrapped in quotes with no escaping so a quote in the value broke the frontmatter outright. Benign values still emit as plain, unquoted scalars.

- The untrusted-content warning banner no longer vanishes from `state get <section>`. The section branch sanitized the section body and then fed the sanitized string back through the section parser, which read the banner's leading `[SECURITY WARNING: …]` line as a `key: value` pair and split it into a pseudo-field — so the canonical marker `references/security-untrusted-content.md` tells agents to look for was present in the bold-field and plain-field extraction modes but absent in section mode, exactly where a whole section of untrusted state is returned. The body is now structured first and the banner attached ahead of it, removing the double parse rather than escaping the banner to survive one that should not happen; all three extraction modes lead with the intact marker, and under `--json` the banner is a `security_warning` sibling key. Banner construction moved to a shared `securityWarningFor` so the sanitizer and this call site cannot drift on format.

- The bash command-safety hook now fails closed when it cannot read the command. All six hooks share a `readStdinWithTimeout` helper that exited 0 on an unread payload, which is right for the five advisory hooks — the statusline, guardrail, sandbox-detect, context-monitor and update-check — where a non-zero exit over a slow pipe would block a tool call or break the statusline for no safety gain. For `bash-safety-hook` it meant a command whose stdin never arrived was never checked, yet nothing said so, which an auto-approving permission mode reads as approval. The helper now takes an `onTimeout` callback, still defaulting to the silent exit the advisory hooks need, and the bash-safety hook supplies one that emits a `deny` naming the unread stdin. `GSD_HOOK_STDIN_TIMEOUT_MS` overrides the 3000 ms default.

- A timed-out test run is no longer recorded as a failing baseline. The baseline capture ran the suite through `execSync`, which signals a timeout by killing the child — surfacing as an error with no exit status — and the old `err.status || 1` collapsed that into a plain `1`, indistinguishable from a suite that genuinely went red. That was a silent verification hole, not a cosmetic one: `compareBaseline` classifies a later failure as new only when the baseline was not already failing, so a baseline wrongly marked failing labelled every subsequent regression as pre-existing and the triage prompt never fired — real breakage reached the verifier mislabelled. Capture and comparison now share one runner so they cannot drift, a timeout records a distinct sentinel that maps to `unknown` rather than `fail`, and a timed-out comparison reports as a timeout advising a re-run instead of masquerading as a regression. The default cap rose to ten minutes, overridable with `GSD_TEST_TIMEOUT_MS`.

- The installer and `--clean` no longer delete through symlinked managed directories. `removeGsdFiles` and the install-time pre-copy clear enumerated the `agents/`, `hooks/` and `skills/` directories with `readdirSync` and unlinked the joined paths, which resolves *through* a directory symlink — so a user who pointed `.claude/agents` or `.claude/skills` at shared storage had their `gsd-*.md` files deleted there, outside the project, the `skills/` site doing it with a recursive `rmSync`. Every enumerating loop is now gated on `lstat` and skips a symlinked directory with a warning rather than resolving it; `existsSync` follows links, so it could not serve as the gate. The sites that `rmSync` the directory entry itself are unaffected, since those unlink the link and not its target.

- An unparseable `settings.json` is no longer silently replaced with an empty one. `readSettings` swallowed the parse error and returned `{}`, and the caller wrote that empty object straight back over the file — so on *every* install, not only `--clean`, a `settings.json` that strict `JSON.parse` rejected lost every key the user had (model, env, permissions) with exit 0 and no warning; a single comment or trailing comma was enough to trigger it. Two changes fix it. Claude Code accepts JSONC in `settings.json`, so a file strict parsing rejects is usually meaningful rather than damaged: it is now read with a comment- and trailing-comma-tolerant parser, and because that recovery still rewrites the file as strict JSON and drops the comments, the original is copied to `settings.json.gsd-backup` first and the reformat reported. A file that neither parser can read is refused outright — the installer exits non-zero and names it — rather than proceeding as if the user had no settings at all.

- Uninstalling GSD no longer takes a user's own hook command with it. `--uninstall` filtered the hook event arrays in `settings.json` at *entry* granularity, removing any entry that contained a GSD command whole — so a user whose own command shared a `PreToolUse` entry with a GSD hook (same matcher, one entry, which is how the settings format encourages you to write it) lost that command. The inner `hooks` array is now filtered instead, and the entry discarded only once nothing is left in it; `SessionStart` and `PostToolUse` had the identical shape and share the same helper.

- A traceability row with an unrecognised status word no longer closes another phase's requirement. The status cell doubled as the signal that a pipe line *is* a traceability row, so a row whose status fell outside `pending`/`in progress`/`complete`/`blocked` was dropped from the parse entirely — and a requirement left with zero surviving rows takes the branch that closes it and ticks its checkbox on the grounds that nothing contradicts the plan. One ordinary word such as `Deferred` therefore closed the requirement, and did so without ever reaching the phase-ownership check, so it could close a requirement the table assigns to a *different* phase. Neither was reported, because the table-detection flag derived from the same filtered list, so a table whose rows were all non-canonical looked like no table at all and the discrepancy went unrecorded. Rows are now identified by the *table* they sit in — consecutive pipe lines whose block carries a Status-headed column or any recognised status — rather than by their own status word, so an uninterpretable status fails closed: it blocks closure, comes back in a `requirements_unreadable_rows` field that `/gsd:execute-phase` now surfaces, and is subject to the ownership check like any other row.

- The roadmap-level requirements safety net now fires, and a plan that under-delivers withholds it. Two connected defects. First, `collectPhaseRequirementIds` matched `**Requirements:**` with the colon *inside* the bold markers, but every producer — `templates/roadmap.md`, the roadmapper, `discuss-phase`, `phase add` — writes it outside, as `**Requirements**:`, so the roadmap branch never matched a real document. That branch is the fallback for a phase whose plans carry no `requirements:` frontmatter, and with the per-plan `requirements mark-complete` step removed from `execute-plan`, such a phase closed nothing, ever. Both spellings are now accepted, and the observable effect is that a phase with a roadmap requirements line will close ids at phase-close that it previously left Pending — the closure that was silently not happening. Second, the roadmap line is a phase-level *declaration* rather than a delivery record, so it is admitted only once every plan in the phase has a summary and no plan delivered less than it declared. A plan that legitimately narrowed its scope during execution used to drop the phase-level line silently, leaving a roadmap-only requirement Pending with no explanation; the narrowing is now named in a `requirements_narrowed_summaries` field alongside the ids it withheld. The gate stays all-or-nothing rather than subtracting only the withheld ids, because requirement ids do not partition work cleanly — a dropped task can be the work behind a requirement the plan never listed — so closing the remainder id-by-id would assert unshipped work is done on the strength of an inference the narrowing just disproved. Making this reachable also required the workflow to stop telling the executor to copy `requirements-completed` verbatim from the plan's declaration: under that instruction delivered always equalled declared and the narrowing path could never fire, so `execute-plan` and the summary template now ask for the ids actually delivered and verified, starting from the declaration and keeping each id whose work landed.
